# B200 (sm_100 / Blackwell) results

All experiments run on a Modal-provisioned single B200 (cap (10,0), 192 GB HBM,
torch 2.9.1+cu128, triton 3.5.1). Modal entry points live under `modal/`:

- `modal/run_correctness_b200.py` — 3 pytest files
- `modal/run_attn_b200.py` (`mode=full`) — `benchmarks/attn_only_all_n.py` sweep
- `modal/run_b200_moe_tune.py` — fwd-config sweep at the MoE shape (with
  subprocess isolation so `wgmma` faults don't poison the GPU)
- `modal/run_gemma4_26b_cossim.py` — Gemma-4-26B-A4B per-layer cos-sim with `--all-layers`

## B200 vs H100 codegen workarounds

Triton 3.5.1 has no TMA on sm_100 yet, so the H100 configs that fit at
`num_stages=2` overflow B200's 232 KB dynamic SMEM, and certain `wgmma`
layouts at `D=512` fault with misaligned addresses. Gates patched into
`flash_attn/attention.py`:

- `_stages(default)` — clamps `num_stages` to 1 on `cap[0] >= 10`. Used at
  most kernel launches as a safe default.
- `is_blackwell` block + warp + stage retuning — applied to fwd, dQ, and
  packed dKV. For fwd at `D >= 512`, `BLOCK_Q=32` (vs 64 on H100) sidesteps
  the `wgmma` fault. **Fwd configs were retuned 2026-04-23** via a 19-config
  isolated subprocess sweep at the real MoE shape (H_Q=16, H_KV=8) across
  N=1K..16K — see `benchmarks/b200_moe_fwd_tune.py`. Winners:
  - `D=512`: `(BQ=32, BKV=32, w=4, s=2)` → **1.11–1.20× SDPA at all N**.
    Previous `(w=8, s=1)` was 0.85×. Counterintuitive: fewer warps + double-
    buffer beats more warps + single-buffer at this small block.
  - `D=256`: `(BQ=128, BKV=128, w=8, s=1)` → 17–18 % faster than the prior
    `BKV=64` at the MoE shape, top at N=1K-2K, within 1 % of best at N≥4K.
  - dQ at `D=512`: `BLOCK_KV_BW=32` (vs 64); packed dKV at `D=512`:
    `BLOCK_Q_DKV=32` (vs 64) — both untuned for B200, room remains.

The sweep also confirmed that **almost every D=512 config except `BQ=32` faults**
with `CUDA_ERROR_MISALIGNED_ADDRESS` (16/19 configs faulted), and the fault
poisons CUDA driver state — even `empty_cache` then fails. The sweep driver
runs each config in its own subprocess so the fault is contained to that one
config and the rest of the sweep continues.

`tests/test_packed_dkv.py` calls the inner kernels directly, so it gets the
same B200-aware block selection in `run_forward_with_lse` / `run_dkv_split` /
`run_dkv_packed` (`_is_blackwell()` helper at top of file).

### Notes

- **D=512 fwd now beats SDPA** (1.04–1.14× across all N) after the 2026-04-23
  retune. Pre-retune was 0.54–0.74×: the BLOCK_Q=32 workaround at the old
  `(w=8, s=1)` left compute under-fed. Switching to `(w=4, s=2)` doubles the
  in-flight stages so the small tile keeps the SMs busy. F+B improved from
  1.21× to 1.39–1.45×; bwd from 1.28–1.52× to 1.30–1.52×.
- **D=256 SWA scales well**: at large N the Triton kernel walks away from
  SDPA — Config A reaches **10.98× fwd** / **12.48× bwd** at N=32K, and
  Config B (Gemma-4-E2B, GQA 8:1) reaches **16.93× fwd** / **17.32× bwd**.
  This is the production hot path.
- **Trade-off at small N for non-MoE shape**: bumping default `BLOCK_KV` from
  64 → 128 was tuned at the MoE shape (H_Q=16, H_KV=8). Config B (E2B,
  H_KV=1, GQA 8:1) regresses at N=1K (fwd 0.77× → 0.63×, bwd 0.97× → 0.57×)
  because the wider BKV under-fills KV with only one KV head. From N≥2K the
  larger tile pays off everywhere. Acceptable since MoE is the target.
- D=512 bwd kernels (dQ at `BLOCK_KV_BW=32`, packed dKV at `BLOCK_Q_DKV=32`)
  were *not* retuned in the 2026-04-23 sweep — only fwd. There is likely
  more bwd headroom on B200.
- Once Triton ships TMA / proper sm_100 autotuning, raising BLOCK_Q back to 64
  on D=512 should give another step up without source changes (the gate
  already branches on `cap[0] >= 10`).

- Smooth monotonic drift through layer 0 → ~23 (cos 1.0 → 0.91), recovers to

  rel_frob peaks ~0.42 mid-stack.
